# 0004 — CI runs on pinned real observations, never synthesized fixtures

**Status:** Accepted · **Date:** 2026-08-18

## Context

Two requirements collide. Prime Directive 1 forbids fabricated data and, explicitly, "fake test
fixtures that mask a broken path." But the validation suite must run on every pull request, and it
cannot re-query MAST each time: that hammers a shared community resource, makes CI slow, and makes
the suite fail whenever the archive has an outage — a failure signal unrelated to code quality,
which trains everyone to ignore red builds.

The tempting resolution is a synthetic light curve with a known injected transit. It is fast,
deterministic, and offline. It is also exactly what the directive prohibits, and for good reason: a
synthetic transit generated by `batman` and then fitted by `batman` tests that the code is
self-consistent, not that it is correct. Every real-world difficulty — systematics, gaps, correlated
noise, contamination — is absent by construction, so the test passes on a pipeline that would fail
on real data.

## Decision

CI runs against **a small snapshot of genuinely-retrieved archive data**, stored via `pooch` with
checksums, carrying full provenance for how and when it was obtained. Real observations, immutable,
available offline.

Separately, a **scheduled** (not per-PR) job re-fetches the same products live and compares against
the snapshot, so upstream drift is detected deliberately.

Synthetic data remains permitted only for injection-recovery — where the injection is the *point* of
the measurement, it is injected into real noise, and results are labeled as recovery statistics
rather than as observations.

## Rationale

The snapshot is not a fixture standing in for real data; it *is* real data, cached. The distinction
matters: a bug that only manifests on real systematics will be caught by this suite and would not be
caught by a synthetic one.

Separating the offline check from the live check means archive outages break the scheduled job,
where that signal is informative, instead of breaking every contributor's pull request, where it is
noise.

## Consequences

- Repository or cache size grows with pinned data. Golden targets are chosen partly for smallness —
  a short-period planet whose transits all fit in one sector, rather than a long-period one needing
  years of coverage.
- The snapshot needs a documented refresh procedure, since archives do reprocess data. Refreshes are
  deliberate, reviewed, and recorded — never silent.
- When the scheduled live job diverges from the snapshot, that is a finding to investigate (did the
  archive reprocess? did calibration change?), not a test to re-baseline reflexively.
